# 排查手册：消息没进 LLM 怎么定位

写于 2026-10-23。那天为一个「群里 @ 她她不回」的问题，
连续三轮误判才对，所以把方法沉淀下来。

---

## 核心原则：先确认断在哪一层，再谈修

**最常见的错误是默认「问题出在刚做的改动上」。**
我那天就是这么错的：看到一批异常请求就断定是新插件失效，
可那批请求发生在插件创建之前。

**任何「行为异常」先查时间线**，确认异常发生在改动之前还是之后，
再决定要不要往改动上归因。

---

## 五层管线与各层的日志特征

```
SnowLuma / OneBot  →  预处理  →  唤醒判定  →  插件钩子  →  LLM 调用
   (适配器层)                        (waking_check)   (on_llm_request /
                                                        on_waiting_llm_request)
```

| 日志里有什么 | 说明断在哪层 | 查什么 |
|---|---|---|
| **什么都没有** | SnowLuma/OneBot 没送来 | `snowluma/logs/snowluma-*.log`，看有无 `[Event]` |
| 只有 `event_bus:116` 那一行 | **唤醒阶段掐的** | `wake_prefix` 能不能命中；At 是否解析成功 |
| 有 `wake_gate` 的 WARN | 插件掐的 | 插件的判定逻辑与组件构成 |
| 有 `stopped event propagation` | 同上，确认是 `stop_event()` 所为 | — |
| `provider_stats` 有新记录 | 通了 | 已进 LLM |

**关键判据**：`core.event_bus:116` 打印的是「消息收到」，
它之后如果没有任何一行，就是在这一行之后的某个阶段被掐了。


### ⚠ 日志实际路径

**配置里写的 `logs/astrbot.log` 跟真实路径不是一回事。**

- 真实落盘位置：`astrbot/data/logs/astrbot.log`
- 相对工作目录 `D:\qqbot` 找；用 `find . -name "*.log" -newermt "<时间>"` 确认

不看日志就等于瞎猜。那天三轮误判，很大程度就是一开始没有日志。

### 临时诊断用 WARNING

默认 INFO 级别下 `logger.debug` 看不见。要定位就在可疑分支打
`logger.warning`，并且**把判断依据一起打出来**：

```python
logger.warning(
    f"掐断！群={group_id} self_id={self_id!r} "
    f"判定={reason} 组件={kinds} 首段文本={...!r}"
)
```

`self_id`、`组件列表`、`文本` 这三项足以还原现场。
`组件` 这样构造：

```python
kinds = [f"{type(c).__name__}({getattr(c,'qq',None) or getattr(c,'sender_id','')})"
         for c in messages]
```

## 组件层的三个坑

### 1. QQ 按**昵称** @ 不生成 At 组件

这是那天最大的坑。实测：

| 群里 @ 的方式 | 组件构成 |
|---|---|
| @昵称（`@<BOT_NICK>`） | `['Plain()']` —— **只有纯文本** |
| @QQ号（`@<BOT_QQ>`） | `['At(<BOT_QQ>)']` |
| @群友 | `['At(群友QQ)']` |
| @全体成员 | `['At("all")']` —— **不是 AtAll** |

**后果**：`message_str.startswith("@<BOT_NICK>")` 不等于 `startswith("<BOT_NICK>")`，
唤醒判定在**上游**就失败了，插件层的任何补救都来不及。

→ 兜底办法：`wake_prefix` 里同时放带 @ 和不带 @ 两种形式。

### 2. `AtAll` 在 aiocqhttp 下不会被产生

```python
# aiocqhttp_platform_adapter.py:352
if m["data"]["qq"] == "all":
    abm.message.append(At(qq="all", name="全体成员"))   # 是 At，不是 AtAll
```

判定时要**两种形态都认**：
```python
isinstance(comp, AtAll) or (isinstance(comp, At) and str(comp.qq) == "all")
```

### 3. `get_self_id()` 可能返回空串

```python
return getattr(self.message_obj, "self_id", "")   # 拿不到就是 ''
```

`str(At.qq) == ""` 永远 False → 所有 @ 她都被判成 @ 别人 → **全员误杀**。
判定拿不到自己的号时**一律放行**，别掐。

## 引用消息会改变 @ 的语义

```
[引用消息(鲸鲸: …)] [At:3825551887] 你再试一次
```

引用里的 `@<BOT_NICK>` 只是**引文文本**，不是真 At 组件。
实际 @ 的目标是**触发者 @ 的人**。
按消息正文判断「@了谁」会得出完全相反的结论。

## 正常但看起来像错的报错

掐断之后 AstrBot 会打这些，**不影响功能**：

```
[ERRO] astrbot.main:275: 主动回复失败:
GeneratorExit
```

`stop_event()` 让 `event.request_llm` 的生成器提前结束，
AstrBot 记成 ERRO。看到这个先别慌，往上找真正的原因。

## 数据库侧的交叉验证

`provider_stats` 是「有没有真的调用 LLM」的地基：

```sql
select start_time, umo, token_input_other + token_input_cached
from provider_stats order by start_time desc limit 10;
```

**但时区要自己换算**：`created_at` 字符串是 UTC，`start_time` 是 epoch 秒。
直接按字符串比对会差 8 小时。

`conversations` 表能看消息原文和发送者 QQ，用来还原现场：

```sql
select content from conversations
where user_id = 'snowluma:GroupMessage:144808575';
```

注意正文里混着 `<system_reminder>`，要按 `split("<system_reminder>")[0]` 切。

## 附：成本优化的三层机制与实测效果

2026-10-23 一天内上线，三个机制叠加：

| 机制 | 作用 | 挂在哪 |
|---|---|---|
| **归档**（memory_tier） | 上下文超阈值就压成摘要，只留最近 15 轮 | `on_llm_request` |
| **本地视觉** | 图片在本地转述成文字，不进云端 | `on_llm_request` |
| **唤醒闸门**（wake_gate） | 群里没叫就不进对话 | `on_waiting_llm_request` |

实测（`provider_stats`，全会话）：

| 阶段 | 均输入 | 均未命中 |
|---|---|---|
| 基线 | 79,399 | 8,979 |
| 三个机制全上后 | **18,822** | **2,805** |

单次降 76%，群聊请求频率降 86%（23.7 → 3.2 次/小时）。

**两个容易被忽略的点**：

1. **省 token 的主力是"不调 LLM"，不是"缩短上下文"。**
   闸门掐断 = 整次请求消失；归档只是把上下文压小。
   能在上游掐的，优先在上游掐。

2. **别用一次性消耗评估收益。**
   当天基线段烧了 7.7M（占 54%），看起来"更费了"，
   但那是上下文失控时的历史债，机制生效后每天都省。
   → 评估要看**稳态**，用均输入/均未命中比总量。
