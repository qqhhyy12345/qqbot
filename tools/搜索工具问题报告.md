## 二、真正的问题：中文搜索结果坍缩

这正是群友「梵蒂冈御史大夫」昨天 22:36–22:37 说的：

> "bing有中文坍缩，你要做防坍缩插件的"
> "不是，直接给你干成字典页了"

### 实测证据

**查询「鸣潮 珂莱塔 养成攻略」→ 只返回 1 条**

```
1. 《鸣潮》官方网站 - Wuthering Waves
   https://mc.kurogames.com/
   摘要：《鸣潮》是一款开放世界动作游戏，主打高自由度的动作战斗玩法……
```

这是**游戏官网首页**，不是攻略。

**查询「鸣潮 1.4 版本 新角色」→ 返回 10 条，但全是垃圾**

```
1. 《鸣潮》官方网站          ← 官网
2. 鸣（汉语汉字）_百度百科     ← 把「鸣」当汉字查了
3. 云·鸣潮 - Wuthering Waves  ← 云游戏页
4. 《鸣》的拼音,鸣字的意思…    ← 汉语字典页
```

**Bing 的中文 RSS 把长查询拆成了「鸣」+「潮」，退化成了汉字词典查询。**

这与群友描述的"直接给你干成字典页"**完全一致**。

### 对照组：搜索本身没坏

| 查询 | 结果数 | 质量 |
|---|---|---|
| 北京天气 | 5 | ✅ 中国天气网、中央气象台、MSN 天气 |
| 南京航空航天大学 | 5 | ✅ 学校官网、百度百科 |
| 2026年世界杯时间表 | 5 | ⚠️ 百度百科、腾讯新闻（偏泛） |
| **鸣潮 珂莱塔 养成攻略** | **1** | ❌ 只有官网 |
| **鸣潮 1.4 版本 新角色** | 10 | ❌ 一半是汉字字典 |

**规律很清楚：查询词越"专有名词+长尾"，坍缩越严重。**

- 通用词（天气、学校）→ 正常
- 专有名词（鸣潮、珂莱塔）→ 被拆词 → 退化成词典

## 三、为什么工具一次都没被调用

工具可用但**零调用**，这是第二个问题——不是故障，是行为。

原因链：

1. 群友问「鸣潮攻略」时，她**答了**：
   > "只是版本一直在更新，我知道的东西可能跟不上，你直接说是哪个角色哪个本，我尽量答。"

   这句话对应的是**人格 prompt 里的保守设定**，而不是搜索能力缺失。

2. 昨天那个场景里，她还没接上 bing 插件（群友是在建议她做插件）。

3. 插件接上之后，**没有人再问过需要查的问题**。今天的对话全是私聊闲聊
   （改备注、吃饭、要不要躺一会儿），群聊也没有需要查的提问。

**结论**：零调用**不能证明工具坏了**，只能说明没有触发条件。
但结合搜索质量坍缩，可以断定：**一旦触发，出来的结果会是垃圾**。

## 六、深度实测：坍缩的真正成因（2026-10-23 18:45 追加）

上面第三节的判断（「Bing 中文把长查询拆成「鸣」+「潮」」）**不准确**。
实测后已修正，以下是硬数据。

### 6.1 参数改不动它

同一批查询，跑遍 5 种参数组合：

| 变体 | 鸣潮 珂莱塔 养成攻略 | 词典页 |
|---|---|---|
| A `www.bing.com` + `format=rss`（现状） | 10 条 | **8** |
| B `www` + `mkt=zh-CN&setlang=zh-hans&ensearch=0` | 10 条 | **8** |
| C `cn.bing.com` + 裸参数 | 10 条 | **8** |
| D `cn` + `mkt/setlang` | 10 条 | **8** |
| E `www` + `ensearch=0&qs=n&form=QBRE` | 10 条 | **8** |

**全部一模一样。** host、语言参数、拼写纠正开关统统无效 → 不是参数问题。

### 6.2 真正的机制：Bing 只检索第一个 token，其余丢弃

RSS 原文 dump（查询「鸣潮 珂莱塔 养成攻略」）：

```
 1. 《鸣潮》官方网站 - Wuthering Waves        ← 真正匹配
 2. 鸣（汉语汉字）_百度百科                   ← 「鸣」的单字条目
 3. 云·鸣潮 - Wuthering Waves                ← 真正匹配
 4. 《鸣》的拼音,鸣字的意思、组词、部首… - 汉语查
 5. 鸣的意思,鸣的解释,鸣的拼音… - 汉语国学
 6. 鸣 míng - 汉典
 7. 鸣怎么读_鸣的拼音 - 新华字典
 8. 鸣 míng - 漢典
 9. 鸣字的含义和寓意 - 十大寓意解析 - 好名道
10. 鸣的读音、意思、部首、笔顺及组词 - 新华字典
```

**9/10 条是「鸣」这个单字的字典页。** 规律：

1. 查询按空格切 token
2. **只有第一个 token（鸣潮）被真正检索**
3. 首 token 若是 Bing 不认识的专有名词 → **单字化**成「鸣」，于是返回「鸣」的词典条目
4. 其余 token（珂莱塔 / 养成攻略）**完全丢弃**

跨查询验证：

| 查询 | 坍缩成 | 结果 |
|---|---|---|
| 原神 甘雨 圣遗物 搭配 | 「原」 | 10 条 / 6 词典页 |
| 崩坏星穹铁道 2.0 角色攻略 | 「崩」 | 10 条 / 3 词典页 |
| 如何提高Python性能 详细教程 | 「如何」 | 10 条 / 1 词典页 |
| 南京 天气 明天 | — | **10 条 / 0 词典页**（南京是常用词，Bing 认识） |
| 甘雨 圣遗物 | — | **10 条 / 0 词典页** |

**结论：不是"长查询"的问题，是"首 token 是 Bing 不认识的专名"就会单字化。**

### 6.3 行为还是概率性的

同一查询「鸣潮 珂莱塔 养成攻略」，第一轮 10 条 / 8 词典页，**第二轮只返回 1 条且干净**。
Bing 服务端有随机性/实验分流 → **不能指望任何一次修复就稳定，必须每次都净化**。

### 6.4 查询改写全部无效

| 变体 | 结果 |
|---|---|
| 引号包专名 `"鸣潮" "珂莱塔"` | 1 条（干净，但**没有珂莱塔的内容**） |
| 全部引号 | 1 条（同上） |
| 连写无空格 | 10 条 / 8 词典页 |
| 只留专名 | 1 条（同上） |
| 换同义表述 | 10 条 / 8 词典页 |
| 加 `site:` 限定 | 10 条 / 8 词典页 |

**没有任何改写能让 Bing 正确检索「珂莱塔」。**

### 6.5 子查询拆分是有效的（唯一被证明有效的手段）

| 原查询 | 单查可用 | 拆分后合并可用 |
|---|---|---|
| 原神 甘雨 圣遗物 搭配 | 4 条（含 6 词典页） | **10 条 / 0 词典页** |
| 崩坏星穹铁道 2.0 角色攻略 | 7 条 | 7 条（多个来源，去重后） |
| 鸣潮 珂莱塔 养成攻略 | 2 条 | 6 条（含噪音） |

关键规律：**「专名 + 1 个修饰词」比「专名 + 3 个修饰词」好得多**。
「甘雨 圣遗物」「星穹铁道 角色」都完全正常。

### 6.6 HTML 回落路径已经死了（独立的 bug）

插件里 RSS 无结果时会回落到 `cn.bing.com` HTML 抓 `li.b_algo`。实测：

| 端点 | HTTP | 字节 | `li.b_algo` | `<a>` 总数 | 可见文本 |
|---|---|---|---|---|---|
| www 桌面版 | 200 | 9,508 | 0 | **0** | 空 |
| m 移动版 | 200 | 58,842 | 0（`b_algo` 只出现在 JS 字符串里） | **0** | 空 |
| cn 桌面版 | 200 | 10,290 | 0 | 0 | 空 |

**Bing 现在给的是纯 JS 壳，一个结果链接都没有。** 这段回落代码等于死代码，
而且每次还多花一次 cookie 预热请求。`_parse_bing` 这个函数目前一次都没成功过。

### 6.7 换源全部走不通（实测，本机网络环境）

| 源 | 结果 |
|---|---|
| `html.duckduckgo.com` | ✗ SSL 握手超时 |
| `lite.duckduckgo.com` | ✗ SSL 握手超时 |
| `searx.be` / `search.bus-hit.me` / `priv.au` | ✗ SSL 握手超时 |
| `mojeek.com` | HTTP 403 |
| `yandex.com` | **「Are you not a robot?」** 人机验证 |
| `so.com`（360） | 200 / 95KB / JS 壳，27 个 `<a>` 里没有结果链接 |
| `sogou.com` | 200 / 54KB / 标题为空 / JS 壳 |
| `quark.sm.cn` | 200 / 1.2KB（被限流降级） |
| `so.toutiao.com` | 200 / 48KB / `<a>` = 0，JS 壳 |

**国外源在这台机器上是网络层不通（TLS 握手超时），国内源全是 JS 渲染 + 反爬。**
→ **Bing RSS 是本机唯一稳定可用的搜索通道**，换源这条路短期内走不通。

### 6.8 修正结论

原报告第三节的「换源 / 拆词检测」两条建议要改：

- **拆词检测 → 升级为「词典页过滤 + 查询拆分 + 坍缩降级」**（6.5 已证明拆分有效）
- **换源 → 降级为长期项**（6.7 证明本机换不了源）
- **新增：修掉 HTML 回落死代码**（6.6）

## 八、百度方案评估（2026-10-23 19:05 追加）

### 8.1 百度网页搜索：纯 HTTP 完全拿不到

实测 4 类端点 × 3 种 header 组合：

| 端点 / 变体 | 结果 |
|---|---|
| `www.baidu.com/s?wd=` 桌面 UA | **「百度安全验证」** 图形验证码 |
| `www.baidu.com/s?wd=` 移动 UA + Referer | 200 但 5,613 字节，**`a=0`**，可见文本只有标题 → JS 空壳 |
| `www.baidu.com/s?wd=&tn=monline_3_dg` | 200 / 13,349 字节，**`a=0`** → JS 空壳 |
| `m.baidu.com/s?word=` | **跳 `wappass.baidu.com/.../captcha/tuxing_v2.html`** 图形验证码 |
| `www.baidu.com/s?wd=&tn=baidurt` | 200 / 55,646 字节，但高频 class 是 `fyb_title×10 / trend×10 / realtime×10` → **这是热搜聚合页，不是搜索结果** |
| `news.baidu.com/ns?word=` | HTTP 500 |
| `news.baidu.com/rss?word=` | HTTP 500 |
| `baike.baidu.com/search/word=` | 200 / 1,697 字节 JS 壳 |
| `zhidao.baidu.com/search?word=` | 200 / 12,986 字节，链接只有「网页/资讯/视频/图片」导航 |

**结论：百度的搜索结果 100% 是 JS 渲染 + 行为风控，纯 aiohttp 一条都拿不到。**
要用百度搜索必须常驻真实浏览器（Playwright/Selenium）执行 JS 并伪装指纹：
几百 MB 内存、单次搜索 3–10 秒、百度改版即失效、IP 被标记就全挂。

### 8.2 但百度联想词 API 完全可用（重要发现）

```
GET https://www.baidu.com/sugrec?prod=pc&wd=<查询>
→ 200, application/json, 无风控、无 JS
```

返回示例：
```json
{"q":"鸣潮 珂莱塔 养成攻略","g":[
  {"q":"鸣潮 珂莱塔 养成攻略视频"},
  {"q":"鸣潮珂莱塔怎么获得"},
  {"q":"鸣潮珂莱塔配队"},
  {"q":"鸣潮珂莱塔入卡池时间"}]}
```

**这是百度自己的中文分词结果 + 真实用户的热门问法**，质量远高于 Bing 对中文的处理。
可以拿它做**查询扩展**：把长查询换成"百度认为用户真正想问的短查询"。

### 8.3 联想词 + Bing RSS 的实测效果

| 原查询 | 直接搜可用 | 联想词合并可用 | 评价 |
|---|---|---|---|
| 崩坏星穹铁道 2.0 角色攻略 | 7/8 | **15/16**（拿到 B 站 WIKI 全角色攻略） | **显著变好** |
| 原神 甘雨 圣遗物 搭配 | 4/10 | 3/3 | 略好 |
| 鸣潮 珂莱塔 养成攻略 | 10/10 | 3/3 | **变差**（丢了攻略页，多了官网） |
| 上海 天气 明天 | 10/10 | 6/6 | **变差**（丢了天气预报网，多了旅游攻略） |

**规律**：
- 对 **5 字以上长专名**（崩坏星穹铁道）有效——sugrec 提供的「崩坏星穹铁道全角色攻略」正好落在 Bing 的有效区间
- 对 **2 字专名组合**（原神+甘雨、鸣潮+珂莱塔）无效——Bing 对这些稳定坍缩
- 对 **本来就不坍缩的查询是负优化**——引入噪音 + 请求量翻 5 倍

所以 sugrec **不能无脑调用**，只能作为「过滤后仍不足」时的二级兜底。

### 8.4 搜索侧根本不需要广告过滤

- **Bing RSS 是纯结果流，不含广告**
- **百度 sugrec 是纯 JSON，不含广告**

只有把搜索源换成百度网页搜索，才需要写广告位过滤（`ec-tuiguang` / `data-placeid` / 商业推广块）。
**换言之：走推荐路线的话，"过滤广告"这个需求用不上。**
"过滤广告"真正有价值的地方是 **fetch_url 抓正文时**——很多网页正文里塞了广告位、
"相关阅读"、"下载APP"等噪音，这正是群友抱怨的「越搜越浅」的来源之一。

## 九、坍缩是概率性的 —— 重试命中率实测

同一查询连搜 3 次（间隔 1.3s）：

| 查询 | #1 | #2 | #3 | 稳定性 |
|---|---|---|---|---|

（格式：总条数 / 词典页数）

**两类坍缩**：
- **稳定坍缩**（4/8 组，3 次全中）：首 token 是 **2 字专名**（原神、鸣潮、黑神话）→ 被单字化且不恢复
- **不稳定坍缩**（首 token 是 5 字以上专名或含数字版本号）→ 重试 1-2 次能撞到正常那次

**重试的价值是条件性的**：只对不稳定组有效，对稳定组是 3 倍请求的纯浪费。
必须配合"过滤后可用数是否达标"作为触发条件，而不是无条件重试。

首次搜索平均可用 **5.0 条**，3 次内最好 **10 条**。

## 十、修正后的方案（按成本从低到高）

### 方案 C（推荐）：Bing 侧自改造
| 步骤 | 做法 | 代码量 | 额外请求 |

| C1 | 词典页过滤（正则） | ~15 行 | 0 |

无状态、无 cookie、无风控，全部在插件内。**成本最低。**

### 方案 B（可选）：加百度 sugrec 做查询扩展

## 十一、实施方案（2026-10-23 19:20 已上线）

浩越拍板 **C + D**，全部改动在 `astrbot/data/plugins/astrbot_plugin_fetch_url/main.py` 内。

### 11.1 方案 C 实现

| 函数 | 职责 |
|---|---|
| `_is_dict_page(title, url)` | 词典页识别：标题特征词 + 词典站域名 + 百度百科单字词条，三条任一命中 |
| `_clean_results(results)` | 剔词典 + URL 去重 + 保首次出现顺序 |
| `_relevant(title, tokens)` | 标题命中查询关键词 → 有效命中 |
| `_enough(results, tokens)` | 够用判定：条数≥3 / 有相关命中 / 来自≥2 个域名 |
| `_split_queries(query)` | 去版本号 token + 首词+后续词 + 前两词，最多 2 个子查询 |
| `_fetch_rss(session, q, n)` | 单次 RSS 请求 |

流程：**原查询 → 过滤 → 不够则重试（≤2 次）→ 仍不够则拆分子查询 → 合并去重**。
子查询拿回全是重复 URL 就止损。

### 11.2 方案 D 实现

- `DROP_TAGS` 扩到 22 个（加 `ins/object/embed/canvas/picture/audio/video/map/track/source`）
- `NOISE_RE` 扩词：`sponsor/overlay/qrcode/download-btn/float-left/fixed-top/pager/pagination`
- 新增 `NOISE_LINE_PAT` + `NOISE_LINE_MAX=12`：独立行的「广告」「相关阅读」「扫码下载APP」
- 新增「相关阅读列表」启发式：容器内 ≥3 个链接且链接文字占比 ≥60%
- 新增「广告图位」启发式：含 `img` 且文字 <30 字

### 11.3 两个差点做成负优化的坑

**① `NOISE_RE` 里加 `app` → CSDN 整页被删**
CSDN 全站是 `<div id="app">` 包着的，`app` 命中独占 token 规则 → 根节点被 decompose
→ 正文 3669 字变 0 字。
**教训：往 NOISE_RE 加词前，先查目标站点的根容器 id/class。**
现在 `app` 已移除，`download`/`fixed`/`float` 也改成带后缀的精确形式。

**② 启发式误删父容器 → 正文全清空**
父容器通常也满足「一堆链接」的判定。修复：**启发式只作用于叶子容器**
（内部无 `div/section/article/ul/ol/table/p/blockquote`）。
