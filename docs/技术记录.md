### 3.4 分层记忆插件（本轮最大收获，压缩 87.5%）

**发现真问题**：查 `provider_stats` 真实账单发现，上下文 96,608 token 里人格卡只占 1,132（**1.2%**），98.8% 是对话历史。继续挖：

- `conversations` 表当前会话 content **305 万字符**
- `agent_runner.config.compression.max_turns = -1`（**不限轮数**），`fallback_max_tokens = 128000`
- **内置压缩是"一次性"的**：`ContextManager.process()` 结果只用于本次请求，`processed_messages` 不回写数据库。每次请求重处理同一批老历史，摘要不留档

这就是"费钱"和"健忘"矛盾的真正来源——不是记不住，是记的东西每次都重新揉一遍、揉完就扔。

**方案：三层记忆**

| 层 | 内容 | 实现 |
| --- | --- | --- |
| L0 | 最近 15 轮原文 | 原样保留 |
| L1 | 更老轮次摘要 | 落盘 `bot-memory/archive/<umo>.md`，**只压一次** |
| L2 | 可检索事实 | 预留，待接 `memory_search` |

**插件实现要点**：

- 挂 `@filter.on_llm_request()`（定义在 `star_handler.py:433`，触发点 `internal.py:307`）
- **执行顺序已核实**：本钩子早于 agent runner 里的内置压缩（`tool_loop_agent_runner.py:829`），所以拿到的是原始历史，轮次索引可靠。仍加了保险：检测到内置摘要标记就跳过
- `req.contexts` 是 **OpenAI 格式 dict 列表**（`[{"role":..,"content":..}]`），不是 Message 对象
- 游标存 `bot-memory/archive/<umo>.meta.json`（`archived_rounds` / `blocks`），不用 kv——透明可审计可手改
- **安全边界：绝不改 `conversations` 表**，只改"本次请求读到的东西"，删插件即恢复
- 降级：摘要失败 → 什么都不改；限频 300s；单次最多归档 30 轮
- 白名单 `ONLY_UMO` 默认只对主人私聊生效

**可调参数**（`main.py` 顶部）：`KEEP_RECENT_ROUNDS=15`、`SOFT_LIMIT_TOKENS=20000`、`MAX_ARCHIVE_ROUNDS=30`、`COOLDOWN_SECONDS=300`

## 四、关键技术认知（踩过才知道）

### 4.1 AstrBot 的上下文压缩是"一次性"的

`ContextManager.process()` 返回的列表只用于当次请求，**不持久化**。所以：

- 每轮请求都在重处理完整历史
- 内置 `llm_compress` 摘要每次重算，内容会漂移
- 想持久化必须自己写插件（`memory_tier` 就是干这个的）

### 4.2 `.ignore` 管不了侧栏

`.ignore` 只喂给 ripgrep（Grep 工具底层），**文件树/侧栏不读它**。`.vscode/settings.json` 也只有 `search.exclude` 和 `files.watcherExclude`，没有文件树折叠项。

想治侧栏只能靠物理手段（移出工作区 + junction 回指）。**本地已定案：侧栏不卡，不做迁移。**

### 4.3 怎么判断插件是否加载

AstrBot 不把插件状态写数据库，`plugins.json` 只是市场缓存，stdout 又没落盘。**最硬的证据是 `__pycache__/*.pyc` 的时间戳**——被 import 过就会刷新，对比进程启动时间即可。

### 4.4 token 账单在哪查

```python
import sqlite3
con = sqlite3.connect(r'file:D:\qqbot\astrbot\data\data_v4.db?mode=ro', uri=True)
cur = con.cursor()
cur.execute("""SELECT rowid, created_at, token_input_other, token_input_cached, token_output
               FROM provider_stats ORDER BY rowid DESC LIMIT 10""")
for r in cur.fetchall(): print(r)
```

`token_input_other` = 新增输入（全价），`token_input_cached` = 缓存命中（约 1/10 价）。

**重要**：改人格卡、改配置、重启都会让 prompt cache 失效，触发一次全量重算（实测一次 96,818 token）。所以**频繁改 prompt 类配置反而费钱**。

### 4.5 日志别读错文件

- `logs/astrbot.log`、`logs/snowluma.log` —— **旧实例的残留**，会停更
- 当前活跃日志：`snowluma/logs/snowluma-YYYY-MM-DD.log`
- AstrBot 的 stdout 至今没落盘（`astrbot/data/logs/` 不存在），排查只能靠间接证据

## 八、2026-10-28 补记：语音转文字拆成独立插件（ASR）

### 8.1 为什么拆

whisper 逻辑原来长在 `listen_bili` 里，只能给 B 站视频用。QQ 语音消息、音频链接都想复用同一套能力，所以拆出 **`astrbot_plugin_asr`**：

- 其他插件 import 一个函数就能转写，不用关心 worker / 模型 / 编码
- `listen_bili` 退回只做 B 站特有的事：BV 解析、playurl 取流、cookie、下载、听完即删

### 8.2 结构

| 文件 | 职责 |
| --- | --- |
| `plugins/astrbot_plugin_asr/core/asr_worker.py` | 子进程，stdin/stdout 各一行 JSON；av 解码 → faster-whisper small int8 CPU → opencc t2s |
| `plugins/astrbot_plugin_asr/core/asr.py` | 公开接口 `transcribe_file` / `transcribe_url` / `delete_temp_audio`；不抛异常、全局串行、单次 ≤15 分钟 |
| `plugins/astrbot_plugin_asr/main.py` | `on_llm_request` 转写 QQ 语音 + tool `asr_transcribe` 转音频直链 |
| `plugins/astrbot_plugin_listen_bili/main.py` | 调 `transcribe_file`；B 站下载与结果格式化 |
| `plugins/astrbot_plugin_listen_bili/core/melody_worker.py` | 只做 librosa 旋律 DSP（BPM / 调性 / 音域 / 走向） |

### 8.3 接口（其他插件怎么用）

```python
from data.plugins.astrbot_plugin_asr.core.asr import transcribe_file

res = await transcribe_file(r"D:\path\to\audio.m4a", max_minutes=5)
# {"ok": True, "text": "...", "duration_s": 123}
# {"ok": False, "error": "..."}
```

- 真正干活的是 `asr_worker.py`，必须用 WorkBuddy 的 Python（`C:\Users/<user>\.workbuddy\binaries\python\envs\default\Scripts\python.exe`）拉起——AstrBot 主环境没有 faster_whisper。路径写在 `core/asr.py` 顶部
- 每次调用拉起一个子进程，模型现加载（~2s），不常驻内存
- 全局锁串行：int8 已经吃满 14 线程，并发没有收益

### 8.4 QQ 语音怎么接的

- 钩子用 `on_llm_request`（触发点 `internal.py:307`，此时 `req` 已建好、早于 runner 启动）
- 把消息链里的 `Record` 就地换成 `Plain` 文字，同时把 `req.audio_urls` 和 `[Audio Attachment: …]` 附件说明摘掉
- **为什么必须摘**：provider 的 `modalities=[]` 会被判成支持全模态，原音频会以 `audio_url` 块进请求；`deepseek-v4.1-flash` 是纯文本模型
- 单条消息最多转 2 条语音；超额的换成提示文字，但音频同样摘掉
- 转写失败也替换成一句说明，绝不把音频漏给文本模型
- 引用消息（`Reply.chain`）里的语音一并处理
- **听完即删**：AstrBot 的 temp 清理要等整轮结束（`pipeline/scheduler.py:101` 的 finally），转写场景更早删更干净。做法是整条消息处理完后（不能单条转完就删，否则同路径的重复语音会 `_resolve_path` 失败）对每个路径 `event.untrack_temporary_local_file()` + `delete_temp_audio()`
- `delete_temp_audio()` 有边界：**只删 `D:\qqbot\astrbot\data\temp` 内的文件**，目录外一律返回 False 不碰；删不掉（占用等）也只返回 False，不抛异常

### 8.5 顺手修的真 bug：子进程协议编码

Windows 下 Python 子进程 stdout 默认是 GBK。旧 `audio_worker.py` 输出中文，父进程按 `utf-8 / "ignore"` 解码 → 中文被当非法字节丢掉，**等于 `bili_listen` 的中文转写一直是残缺的**。

修复：两个 worker 的 `main()` 里 `sys.stdin.reconfigure(encoding="utf-8")` + `sys.stdout.reconfigure(encoding="utf-8")`（stdin 也改，因为路径里可能有中文）。

### 8.8 顺手修好 voice_tool（模型自选语音）

**病灶**：`provider_tts_settings.enable = false`（关掉随机自动语音，本来是对的）会让 `get_using_tts_provider_async()` 在 `manager.py:272` 直接 `return None` —— AstrBot 把"随机语音开关"和"取 TTS 服务"绑在同一个判断里。于是 `send_voice` 每次都回「现在没有可用的语音服务，改用文字」，插件从 10-22 装上起**一直空转**：`data/temp` 里 17 个 `edge_tts_*.wav` 全停在 10-22 21:41（装机测试那几分钟），之后零新增。会话级偏好表里也没有 TTS 偏好可以绕过。

**修法**（`main.py`）：

- `_resolve_tts_provider()`：先 `get_using_tts_provider_async(umo)`（保留会话级偏好），取不到退 `context.provider_manager.curr_tts_provider_inst`（初始化时按 `provider_tts_settings.provider_id` 解析，**不看 enable**，`manager.py:391-400`），再退 `get_all_tts_providers()[0]`
- **返回值改状态码**：`已发送=1` / `未发送=0（原因）`。模型拿到 `已发送=1` 就不必再确认、不必重发（以前回的是长句"已经用语音说出去了…"）
- **发完即删**：`get_audio()` 产出的 wav 落在 temp，发送后（失败也）用 `_delete_temp_audio()` 删掉；只删 `get_astrbot_temp_path()` 目录内的文件
- `edge_tts` 的 mp3 中间文件由引擎自己删，只剩 wav 需要清

**冒烟 14 项全过**：成功返回 `已发送=1` 且音频删净、`using` 为 None 时 fallback 生效、无 TTS / 合成失败 / 发送失败 / 空文本都回 `未发送=0`、目录外文件照发但不删。

> 遗留：10-22 那 17 个 `edge_tts_*.wav`（约 6MB）还在 `data/temp`，新逻辑只管新生成的，老的要清得手动删。
